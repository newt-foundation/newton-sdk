# Policy Packs [Use Newton policy packs to enforce risk, compliance, and oracle checks before vault actions execute.]

Newton vault policy packs combine Rego policy logic with policy data oracles. The oracle gathers the external data needed for a decision, then the Rego policy evaluates that data against the vault's configured parameters.

In VaultKit 2.1, each published pack implements the `PolicyPack` contract from `@newton-xyz/policy-core`. Declare packs with `definePolicy(...).with(pack)`; use `defineOracle(...)` when authoring your own compatible oracle.

```typescript
import { definePolicy } from '@newton-xyz/vaultkit'
import { vaultsfyi } from '@newton-xyz/policy-pack-vaultsfyi'

const policy = definePolicy({ chainId: '8453', env: 'prod' })
  .with(vaultsfyi)
```

In the Newton dashboard, use **Explore Data Oracles** to browse available data oracles, inspect the data they provide, and add the relevant oracle to a policy. Vault policy packs can combine multiple oracles, so a single vault action can be checked against risk, compliance, and market data before it is approved.

The open-source policy packs live in [newt-foundation/newton-policy-packs](https://github.com/newt-foundation/newton-policy-packs). Data providers can follow the repo's [CONTRIBUTING guide](https://github.com/newt-foundation/newton-policy-packs/blob/main/CONTRIBUTING.md) to add a pack that other developers can reuse in Newton-powered applications.

For more detail on how packs work, how they are implemented, and how to build policies from them, see [Policy Packs](/developers/guides/policy-packs).

:::note
The canonical deployment source is [`newton-policy-packs/deployments.json`](https://github.com/newt-foundation/newton-policy-packs/blob/main/deployments.json). Look up a pack's policy address with `newton-cli policy packs`, which reads that file, instead of copying it from a snapshot. See [Pack Policy Addresses](#pack-policy-addresses).
:::

## Pack Policy Addresses

Each published pack is a deployed `NewtonPolicy`. Resolve its address for your chain and environment with `newton-cli`, which reads [`deployments.json`](https://github.com/newt-foundation/newton-policy-packs/blob/main/deployments.json):

```bash
# Every pack published on Base
newton-cli --chain-id 8453 policy packs list

# One pack, machine-readable
newton-cli --chain-id 8453 policy packs show --pack vaultsfyi --format json
```

The JSON output carries `policy` and `policy_data` as the same address, plus `wasm_cid` when the pack publishes an oracle. Put the `policy` value in your `policies.json` and pass that file to `newton-cli policy-client set-policies`; see [Using the CLI](/developers/guides/policy-packs#using-the-cli). The commands use the `prod` environment unless `DEPLOYMENT_ENV` is set. Pass `--env stagef` for staging, or `--catalog <path-or-url>` to read a different catalog.

When a pack is not published for your chain and environment, `policy packs show` exits with `no published policy for pack`, or with `unknown pack` when the catalog has no entry for that pack at all.

## Composing Policy Packs

Vault policy packs are most useful when combined. For example, a regulated yield vault might require:

- Webacy depeg-risk checks for pegged-token exposure
- Chainalysis sanctions screening for the depositor address
- Vaults.fyi risk checks before accepting additional capital
- RedStone oracle divergence checks before curator reallocations

The result is a vault whose rules are explicit, inspectable, and enforced before execution.

The three Xerberus packs are built to run together as one gate for exposure-increasing actions: an exit quote for the asset, a what-if for the portfolio, and a common-cause check across venues. Pass the same `window` to all three so every result comes from one Xerberus snapshot.

For custom oracles, policy-level `_policy` params, bare policies, manifest introspection, and provenance classification, see [Policies](/developers/vaults/sdk/policies) and [Custom Oracles](/developers/vaults/sdk/custom-oracles).
