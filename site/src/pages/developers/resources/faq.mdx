# FAQ & Troubleshooting [Frequently asked questions and solutions to common issues with Newton Protocol — API keys, policy evaluation, chain support, error codes, and debugging.]

## General FAQ

:::details[What is Newton Protocol?]
Newton Protocol is a decentralized policy engine for onchain transaction authorization, built as an EigenLayer Actively Validated Service (AVS). It lets you encode, verify, and enforce rules — such as spend limits, sanctions screening, or KYC gates — directly within smart contracts. See [What is Newton?](/developers/overview/about) for a full overview.
:::

:::details[What chains does Newton support?]
Newton currently supports **Ethereum Sepolia** (`11155111`) as both a source and destination chain and **Ethereum mainnet** (`1`) as a source chain, plus policy execution on **Base** (`8453`), **Base Sepolia** (`84532`), **Robinhood Chain testnet** (`46630`) and **Arc testnet** (`5042002`). See [Supported Networks](/developers/concepts/multichain#supported-networks).
:::

:::details[How do I get an API key?]
Go to [dashboard.newton.xyz](https://dashboard.newton.xyz/), sign in, and click **API Keys** in the left navigation — your key is already generated. See [Getting an API Key](/developers/overview/dashboard-api-keys).
:::

:::details[What programming languages can I use for data oracles?]
Newton data oracles compile to WebAssembly (WASM) components. You can write them in:
- [JavaScript](/developers/advanced/javascript-wasm-guide) (using ComponentizeJS)
- [Python](/developers/advanced/python-wasm-guide) (using componentize-py)
- [Rust](/developers/advanced/rust-wasm-guide) (using cargo-component)

Any language that compiles to WASM and supports the WIT interface can be used.
:::

:::details[What is the difference between Standard and Direct validation?]
**Standard validation** (`_validateAttestation`) checks an attestation that the aggregator has already recorded onchain with `respondToTask`, comparing it against the stored hash. It works once that response is onchain.

**Direct validation** (`_validateAttestationDirect`) verifies the task, the response, and the operators' BLS signatures inside your own transaction, so it does not wait for the aggregator's onchain response.

Neither path reads the PolicyClientRegistry. Both check the attestation against your contract's policy ID.

See [Validation Methods](/developers/overview/core-concepts#validation-methods) for details.
:::

:::details[How long does policy evaluation take?]
A task typically goes from submission to attestation in under a second, around 200 ms at the median on Base Sepolia testnet. See [Consensus & Security](/developers/concepts/consensus-security) for how operators reach agreement.
:::

:::details[Can I test policies without deploying on-chain?]
Yes. Use SDK `simulatePolicy` or Gateway `newt_simulatePolicy` to run the configured set’s optional WASM and Rego without an application transaction or BLS attestation. You can also test individual components:
- `newt_simulatePolicy` — test Rego policy logic with provided inputs
- `newt_simulatePolicyData` — test a WASM data oracle
- `newton-cli regorus eval` — evaluate Rego locally with Newton crypto extensions

See [Testing & Debugging](/developers/resources/testing-debugging).
:::

:::details[What is the difference between a Policy and a PolicyClient?]
A **Policy** is a reusable Rego program that defines evaluation logic (e.g., "block transactions over $10,000"). A **PolicyClient** is a smart contract that references a specific policy and its configuration parameters (thresholds, allowlists). Multiple PolicyClients can use the same Policy with different parameters. See [Core Concepts](/developers/overview/core-concepts).
:::

## Common Errors

:::details[TaskAlreadyExists - task ID already recorded]
**Cause:** The Task Manager already has a task recorded under the new task's ID. The gateway derives every task ID from a new random UUID, so resubmitting the same intent creates a new task and does not raise this error.

**Fix:** Resubmit the request; it gets a new task ID.
:::

:::details[InvalidAttestation - your contract rejected the attestation]
**Cause:** `InvalidAttestation()` is not a Newton contract error. Policy client contracts, including the examples in these docs, define it and revert with it when `_validateAttestation` or `_validateAttestationDirect` returns `false`.

**Common reasons:**
- In direct mode the policy denied the intent: `_validateAttestationDirect` returns the quorum-signed `taskResponse.allowed`
- The task was challenged, and the TaskManager returns `false` for a challenged task

**Fix:** For a denial, read the per-policy results rather than retrying. A mismatched policy ID, intent sender or chain ID reverts earlier with `Unauthorized(reason)`, and signature, hash, expiry and replay failures revert inside the TaskManager with their own errors. See the [error selector table](/developers/reference/error-reference#on-chain-error-selectors).
:::

:::details[InvalidRequest: policy client has an empty policy set]
**Cause:** `newt_createTask` reads the policy set before it replies, so a PolicyClient with no policies fails with HTTP 400 `{"InvalidRequest":"policy client 0x... has an empty policy set"}`. `newt_sendTask` accepts the task first and reads the set afterwards, so the same problem arrives as a failed task on the WebSocket topic. An address that is not a PolicyClient on the chain you are calling fails the owner check first, with HTTP 500 `{"Internal":"failed to query on-chain owner for policy client 0x...: ..."}`.

**Fix:** Verify:
1. The PolicyClient address is correct and deployed on the chain you are calling
2. The PolicyClient has a policy set (use `newton-cli policy-client show`)
:::

:::details[AuthenticationFailed or AuthorizationFailed: API key rejected]
**Cause:** A request without an API key gets HTTP 401 `{"AuthenticationFailed":"missing or invalid API key"}`. An unknown or revoked key gets HTTP 401 with an empty body. A key without the method's permission gets HTTP 403, for example `{"AuthorizationFailed":"RpcWrite permission required"}`.

**Fix:**
- Send the key in an `Authorization: Bearer <key>` or `X-API-Key` header
- Check that your key has the permission the method needs (`rpc_read` for simulations and reads, `rpc_write` for task submission and writes, `rpc` for both)
- Verify the key has not been revoked
:::

:::details[WASM oracle returns empty or unexpected data]
**Cause:** The WASM component's `run` function is not returning valid JSON, or the HTTP fetch is failing silently.

**Fix:**
1. Test locally: `newton-cli --chain-id 11155111 policy simulate-wasm --wasm-file policy.wasm --input-json '{}'`
2. Verify your `run` function returns a JSON string (not an object)
3. Check that HTTP requests use the correct URL and headers
4. Ensure secrets are stored if your oracle requires API keys
:::

For a complete list of error codes, see the [Error Reference](/developers/reference/error-reference).
