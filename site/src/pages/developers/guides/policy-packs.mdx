# Policy Packs [Newton policy packs are deployed policies with typed schemas, npm bindings, and a published onchain address per chain.]

A **policy pack** is a prebuilt policy published for Newton. Each pack is a deployed `NewtonPolicy` with its Rego rules and, when it calls an external API, a WASM oracle. Instead of writing and deploying your own policy, you add the pack's policy address to your PolicyClient's policy set, set its params, and upload any API secrets the pack requires.

Each pack ships:

- A deployed `NewtonPolicy` on each chain it supports.
- Open-source Rego and oracle code in [`newton-policy-packs`](https://github.com/newt-foundation/newton-policy-packs).
- JSON schemas for params, secrets, and per-call `wasmArgs`.
- A typed npm package such as `@newton-xyz/policy-pack-vaultsfyi`.
- Canonical deployment metadata in [`newton-policy-packs/deployments.json`](https://github.com/newt-foundation/newton-policy-packs/blob/main/deployments.json), which `newton-cli policy packs` reads.

Packs compose as entries in your PolicyClient's ordered policy set. Each pack evaluates its own params and oracle output, and the client allows an intent only when every policy in the set allows. See [Composing Policies and Oracles](/developers/guides/composing-policy-sets).

## How to Use Packs

There are two ways to use a pack: the [Newton Dashboard](https://dashboard.newton.xyz) (no CLI required) and [`newton-cli`](/developers/reference/command-line-tool). Both use the same open-source packs in the [`newton-policy-packs`](https://github.com/newt-foundation/newton-policy-packs) repo and the same catalog, [`deployments.json`](https://github.com/newt-foundation/newton-policy-packs/blob/main/deployments.json). Pick whichever fits your workflow.

### Using the Dashboard

The dashboard lets you browse the available data oracles, add one to your policy, configure its secrets and params, simulate, and deploy, all from the browser.

:::note
This tutorial focuses on the pack-specific steps. For signing in, generating an API key, and the full project lifecycle, see [Using the Dashboard](/developers/guides/using-the-dashboard).
:::

::::steps
### Open a project in the policy editor
    Sign in at [dashboard.newton.xyz](https://dashboard.newton.xyz) and open a project to reach the policy editor. If you haven't created one yet, follow [Using the Dashboard](/developers/guides/using-the-dashboard) to create a project and set a PolicyClient. A new project starts with an empty **Data Oracles** sidebar, which shows "Data Oracles not found. Explore Data Oracles and add to your smart contract."

### Open Discover Data Oracles
    Click **Add Data Oracles** in the sidebar. The **Discover Data Oracles** modal lists the available packs (**Chainalysis**, **vaults.fyi**, **Webacy**, and **RedStone**) plus a **Custom Data Oracle** option for your own deployed `PolicyData` address. The **Learn more about Policy Packs** link points back to this guide.

    {/* TODO: add screenshot - "Discover Data Oracles" modal listing Chainalysis, vaults.fyi, Webacy, RedStone, and Custom Data Oracle */}
    <img src="/images/packs-dashboard-discover.png" alt="Discover Data Oracles modal listing the available policy packs" />
  
### Pick a pack
    Select a pack to open its detail view. The **Overview** describes what the pack checks, and **Resources** links to the provider's **Website** and docs. When you're ready, click **Continue**.

    {/* TODO: add screenshot - a pack detail / Overview view (e.g. vaults.fyi) with the Continue button */}
    <img src="/images/packs-dashboard-detail.png" alt="Policy pack detail view showing the Overview and Continue button" />
  
### Configure secrets and params
    Continue opens the setup form. Packs that call authenticated APIs prompt for a **Secret Key** (paste the value from the provider); packs that don't show **No Secret Required**. Selecting a built-in pack also pre-fills a reference Rego template, default parameters, and the list of secrets the pack needs, so you start from a working baseline. Secrets are encrypted client-side and uploaded per `PolicyData` address. See [Deploying with CLI](/developers/guides/deploying-with-cli).

    {/* TODO: add screenshot - the Secret Key / Configure setup form with a key/value field */}
    <img src="/images/packs-dashboard-secrets.png" alt="Data oracle setup form for entering a pack's secret key" />
  
### Reference the pack in Rego
    The pack now appears in the **Data Oracles** sidebar. The configure panel (previous step) gives you the deny rules to copy into your Rego. Read the pack's output under its pack id, for example `data.wasm.vaultsfyi.risk_score`, and the thresholds you configured under `data.params.<pack-id>.*`. Add more packs to compose a multi-oracle policy; see [Chaining Data Oracles](/developers/guides/chaining-data-oracles).
  
### Simulate
    Click **Test** to run the full pipeline against sample inputs: every oracle executes, outputs merge into `data.wasm`, and your Rego is evaluated. The output panel shows the allow/deny result and the merged data the policy saw. Use it to confirm your references resolve before deploying. See [Testing Policies](/developers/guides/testing-policies).

    {/* TODO: add screenshot - simulation output panel showing the allow/deny result */}
    <img src="/images/packs-dashboard-simulate.png" alt="Simulation output panel showing the policy allow or deny result" />
  
### Deploy
    When the policy behaves correctly, click **Publish**. The dashboard uploads your Rego and schemas to IPFS, deploys the `PolicyData` and `NewtonPolicy` contracts, and binds the policy to your PolicyClient. For deployment details and mainnet allowlisting, see [Using the Dashboard](/developers/guides/using-the-dashboard#deploy).

### Using the CLI

`newton-cli` uses a pack by its published policy address. You never build or deploy the pack yourself; you add it to your PolicyClient's policy set. You need a deployed PolicyClient that you own, the CLI installed (`curl -L cli.newton.xyz | sh && newtup`), and `API_KEY`, `RPC_URL` and `PRIVATE_KEY` set. `policy-client set-policies` also loads the CLI config, so set `eth_rpc_url`, `gateway_url` and `signer` in `~/.newton/newton-cli.toml` or as `NEWTON_CLI__` variables first. See [Deploying with CLI](/developers/guides/deploying-with-cli) for the full setup.

::::steps
### Find the pack's policy address
    List the packs published on your chain, then resolve the one you want:

    ```bash
    newton-cli --chain-id 11155111 policy packs list
    newton-cli --chain-id 11155111 policy packs show --pack vaultsfyi --format json
    ```

    The CLI reads the canonical [`deployments.json`](https://github.com/newt-foundation/newton-policy-packs/blob/main/deployments.json) catalog. With `--format json`, each row carries `policy` and `policy_data`, which are the same address (the catalog still names the key `policyData`), plus `wasm_cid` when the pack publishes an oracle. Both commands use the `prod` environment unless `DEPLOYMENT_ENV` is set; pass `--env stagef` for staging. Copy addresses from this output, not from GitHub.

### Add the pack to your policy set
    Write a `policies.json` with one entry per policy, in evaluation order. Put the pack's `policy` value in `policy`, its params in `params`, and an expiry in blocks in `expire_after`:

    ```json
    [
      {
        "policy": "0xPackPolicy",
        "params": {},
        "expire_after": 7200
      }
    ]
    ```

    Fill `params` with values that match the pack's params schema; each pack page in the [VaultKit catalog](/developers/vaults/policy-packs) lists its params. Then set the policies on your PolicyClient and read the set back:

    ```bash
    newton-cli policy-client set-policies \
      --client 0xYourPolicyClient \
      --policies policies.json \
      --private-key $PRIVATE_KEY \
      --rpc-url $RPC_URL

    newton-cli policy-client show --client 0xYourPolicyClient --rpc-url $RPC_URL
    ```

    `set-policies` is owner-only and replaces the whole set, so list every policy the client needs in each call. A set holds 1 to 8 entries, and the client allows an intent only when every entry allows. To compose packs, add one entry per pack. To add your own rule next to a pack, [deploy your own policy](/developers/guides/deploying-with-cli) and add it as another entry. The same pack can appear more than once with different params.

### Upload the pack's secrets
    For packs that call authenticated APIs, read the pack's secrets schema, then upload the keys encrypted, scoped to your PolicyClient and the pack's policy address:

    ```bash
    newton-cli --chain-id 11155111 secrets get-schema \
      --policy-address 0xPackPolicy \
      --rpc-url $RPC_URL

    cat > secrets.json <<'EOF'
    { "VAULTS_FYI_API_KEY": "sk-prod-xxxxxxxxxxxx" }
    EOF

    newton-cli --chain-id 11155111 secrets upload \
      --secrets-file secrets.json \
      --policy-client 0xYourPolicyClient \
      --policy-address 0xPackPolicy \
      --api-key $API_KEY
    ```

    Secrets are scoped per chain, PolicyClient, and policy address, so a pack published at a new address needs its secrets uploaded again. Packs that need no credentials skip this step. See [Encrypting Secrets](/developers/advanced/encrypting-secrets) for the wire protocol.

### Simulate
    Before going live, simulate the whole set with `newt_simulatePolicy` (SDK `simulatePolicy`). It runs each policy's oracle and Rego for your PolicyClient, with one `wasmArgs` slot per entry in set order. To check that one pack's uploaded secrets resolve, call `newt_simulatePolicyDataWithClient` with the pack's policy address. See [Testing Policies](/developers/guides/testing-policies#simulate-the-full-policy-set).
