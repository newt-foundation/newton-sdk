# Composing Multiple Policies [Gate one action on several independent signals by giving each signal its own Newton policy. How a policy set is evaluated, how to write Rego for one signal, and how to simulate the whole set end-to-end.]

A policy can have at most one WASM oracle. To gate an action on a set of independent signals, create a policy for each signal and add them to the policy client's set. Each policy will run its own oracle and evaluate its own Rego; the client's verdict is the AND of the set so only one need deny the action.

This guide explains how a policy set is evaluated, how to write the Rego for a single policy in the set, and how to simulate the whole set before deploying.

## When to compose

| Goal | Shape |
|------|-------|
| Gate a deposit on vault risk only | One policy |
| Gate a deposit on vault risk **and** depositor reputation | **Two policies** in the client's set |
| Gate on risk **and** sanctions **and** oracle divergence | **Three policies** in the client's set |

If you only need one signal, see [Writing Data Oracles](/developers/guides/writing-data-oracles) and [Writing Policies](/developers/guides/writing-policies). This guide builds on both.

## How a set is evaluated

Each policy is evaluated in isolation. The output of its oracle is available in that policy's `data.wasm` and its parameters are in `data.params`. This means that two policies could both define a top-level `score` without interfering with each-other.

The network:

1. Runs each policy's WASM oracle, if it has one, with that policy's `wasm_args` and its own stored secrets.
2. Evaluates each policy's Rego against its own `{ params, wasm }` context.
3. ANDs the per-policy verdicts into one decision, and returns the per-policy results alongside it.

:::note
Because nothing merges across policies, a policy's oracle no longer needs to namespace its output under a pack id to avoid collisions. Newton's [policy packs](/developers/guides/policy-packs) still wrap their output under a pack-id key, so read those from `data.wasm.<pack-id>` as their documentation shows.
:::

## Writing Rego for one policy in the set

The recommended pattern within a policy is a **deny set**: each rule adds a reason string to `deny` when a condition fails, and the policy allows only when no deny rule fires. Multiple simultaneous failures then coexist instead of conflicting, so the policy can never accidentally fail open when two rules fire at once.

```rego
package vault_risk

import rego.v1

default allow := false

# Allow only when no deny rule fires.
allow if count(deny) == 0

deny contains msg if {
    score := data.wasm.vaultsfyi.risk_score
    floor := data.params.risk_score_floor
    score != null
    score < floor
    msg := sprintf("risk score %v below floor %v", [score, floor])
}

deny contains "tvl drawdown 24h exceeded" if {
    data.wasm.vaultsfyi.tvl_drawdown_24h_pct > data.params.tvl_drawdown_24h_max_pct
}

# Fail closed if the oracle errored.
deny contains msg if {
    err := data.wasm.vaultsfyi.error
    msg := sprintf("oracle error: %v", [err])
}
```

The second signal is a second policy with its own `package`, its own oracle and its own deny rules. Neither policy can read the other's data, and the client denies the action if either one does.

For Rego language details — `if`, `contains`, `sprintf`, comprehensions — see the [Rego Syntax Guide](/developers/advanced/rego-syntax-guide).

## Simulating the set

Call `newt_simulatePolicy` to simulate the entire set at once. Pass one `wasm_args` entry per policy in set order, and read the per-policy verdicts back out of `policies[]`.

:::code-group
```bash [Gateway RPC]
curl -X POST https://gateway.testnet.newton.xyz/rpc \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $NEWTON_API_KEY" \
  -d '{
    "jsonrpc": "2.0",
    "method": "newt_simulatePolicy",
    "params": {
      "policy_client": "0xYourPolicyClientAddress",
      "chain_id": 11155111,
      "intent": {
        "from": "0xf39Fd6e51aad88F6F4ce6aB8827279cffFb92266",
        "to": "0xb1aD5f82407bC0f19f42b2614fb9083035a36b69",
        "value": "0x0",
        "data": "0x",
        "chain_id": "0xaa36a7",
        "function_signature": "0x"
      },
      "wasm_args": [
        "7b227661756c74223a22307830227d",
        "7b22746f6b656e223a22307830227d"
      ]
    },
    "id": "7ca6621b-7aa4-4bb7-a896-1f2b58a18c78"
  }'
```

```typescript [SDK]
import { createWalletClient, http } from 'viem'
import { privateKeyToAccount } from 'viem/accounts'
import { sepolia } from 'viem/chains'
import { newtonWalletClientActions } from '@newton-xyz/sdk'

const client = createWalletClient({
  account: privateKeyToAccount(process.env.PRIVATE_KEY as `0x${string}`),
  chain: sepolia,
  transport: http(),
}).extend(newtonWalletClientActions({
  apiKey: process.env.NEWTON_API_KEY!,
}))

const result = await client.simulatePolicy({
  policyClient: '0xYourPolicyClientAddress',
  chainId: 11155111,
  intent: { from: '0x...', to: '0x...', value: '0x0', data: '0x' },
  // one entry per policy in the set, positionally aligned
  wasmArgs: ['0x7b227661756c74223a22307830227d', '0x7b22746f6b656e223a22307830227d'],
})

console.log(result.allowed)
for (const p of result.policies ?? []) {
  console.log(p.policy_index, p.policy, p.allowed)
}
```
:::

:::note
If a policy requires secrets, upload them against that policy's address first (see [Uploading & Accessing Secrets in Oracles](/developers/guides/secrets-in-oracles)). `newt_simulatePolicy` requires ownership of the PolicyClient when at least one policy in the set has a secrets schema. To iterate on a single oracle in isolation, use `newt_simulatePolicyData` with inline secrets.
:::

## Deploying the set

Set the whole ordered set of policies on the client with `setPolicies`. Order is significant and repeats are legal.

- **Newton Dashboard** — the policy editor deploys each policy and writes the resulting set onto your policy client. This is the recommended path today. See [Using the Dashboard](/developers/guides/using-the-dashboard).
- **CLI** — deploy each policy with `newton-cli policy deploy`, then bind the ordered set to the client with `newton-cli policy-client set-policy`.
